# Benchmark publishing contract

## Contents

1. Private evidence
2. Public evidence
3. Ledger completeness
4. Report structure
5. Final audit

## Private evidence

Private storage may contain exact repository identity, reference changes and SHAs, prompts, patches, validation logs, judge identities and verdicts, raw events, source reconciliation, and portable harness archives.

Attach artifacts to the private page or object store. A local-machine path is not an artifact. Preserve raw evidence and place corrections beside it rather than silently editing history.

Keep these live documents synchronized:

- executive-first internal decision report;
- detailed candidate cohort summary;
- no-context benchmark runbook;
- evaluation ledger and its default filtered view;
- checksum-verified harness archive.

## Public evidence

Public `ai-config` material may contain only privacy-safe aggregates and generic workload labels. Exclude:

- private repository, team, product, task, PR, page, symbol, path, commit, session, and fingerprint identifiers;
- prompts, patches, raw answers, hidden contracts, judge keys, and source excerpts;
- private Notion URLs and local-machine paths;
- credentials, auth state, environment values, and provider tokens.

Keep protocol cohorts versioned separately. Label within-experiment evidence, exploratory treatment, policy decisions, task-class transfer, censoring, and unmeasured roles explicitly.

## Ledger completeness

Every final trial entry needs:

- exact treatment and workload;
- reference and calibration metadata;
- full private prompt and rubric;
- patch, native validation, frozen validation, and raw timing artifacts;
- every judge score, handoff, strengths, defects, documentation assessment, and follow-up;
- source-reconciled handoff and engineer carry/repair/redrive assessment;
- raw, 429-normalized, and provider-incident timing;
- provider error counts, cost, patch size, value scores, and unambiguous rank direction;
- pricing or compliance correction artifacts;
- evidence stage, status, limitations, and report link.

Mark an entry Final only after calibration, validation reconciliation, the full blind panel, source reconciliation, metrics, and artifact upload are complete.

The default database view should show final production implementation evidence, not queues, archives, or canceled work. Keep separate views for weighted value, Quality:Value, all final outcomes, queue/backlog, evaluation definitions, and historical cohorts.

## Report structure

Lead with actions:

1. Recommended Default and SLOW routes.
2. Explicit challengers and stopped routes.
3. What developers should do now.
4. Strongest matched evidence and uncertainty.
5. Links to detailed pages, ledger views, and artifacts.

Do not lead with a fragile or unrepresentative trial. Avoid narrating harness history unless it changes how evidence should be interpreted. Hide detail in toggles or linked pages only after the top-level decision remains understandable without opening them.

For HTML:

- support light and dark color schemes with sufficient contrast;
- use responsive tables and readable mobile layout;
- avoid screenshots that do not establish a result;
- embed or upload artifacts instead of linking to local files;
- validate links, headings, numeric consistency, and source privacy;
- open the final local HTML for the operator.

## Final audit

Before publication:

1. Recompute every summary from machine-readable evidence.
2. Check that all named winners satisfy validity, compliance, and handoff gates.
3. Verify that raw time, 429-normalized time, and provider sensitivity are not conflated.
4. Verify that provider incidents are not charged to model quality and uncensored protocol failures are not hidden.
5. Search public files for private URLs, paths, identifiers, prompts, and source details.
6. Check JSON syntax, HTML structure, report arithmetic, database filters, attachments, and portable archive checksums.
7. Inspect the final diff and exclude personal configuration or unrelated work.
